# 设计 vs 现状对照

本文对照的是两样东西：设计意图，和当前 main 源码实际要求的操作。只读源码整理，没改代码，也没做真人测试。文中的时间都是源码里的数值，不是实测延迟。

设计意图（三步）：**张掌起阵 → 指宫捏合锁定 → 按宫位做施法手势。**

## 一、操作流程

| 步骤 | 设计 | 代码实际要求 | 位置 |
|---|---|---|---|
| 起阵 | 张掌 | 张掌稳定 300ms | `GestureSmoother.ts:40` |
| 瞄准 | 指宫 | 食指指向，停 100–200ms 出现 Armed | `TargetSelectionController.ts:77` |
| 锁定 | 捏合 | 捏合 | `TargetLockPinchDetector.ts` |
| — | 无 | **松开捏合**（各术控制器等 80ms 的「锁后释放」） | `ReadyMotionCastController.ts`、`KanPullController.ts`、`ZhenFlickController.ts` |
| — | 无 | **对位 180ms** | `SpellCastController.ts:101` |
| — | 无 | **张掌或捏合保持住，蓄势 340–450ms**；中途姿势断开，就回到对位重新蓄 | `SpellCastController.ts:97-115`、`SpellDefinition.ts` 的 `chargeMs` |
| — | 无 | **READY 后手掌静止 120ms** | `ReadyMotionCastController.ts:66` 等 |
| 施法 | 做手势 | 做手势，要求连续两帧都认出 | 各术控制器的 CANDIDATE → CONFIRMED |

**影响：** READY 之前做的施法动作会被直接丢弃（`ReadyMotionCastController.ts:57` 的 `ACTION_BEFORE_READY`），也不会缓存到 READY 之后再用。按「锁完马上施法」的思路去操作，动作永远不生效。

震术还有一个特例：它的施法手势本身是「捏合蓄雷后弹开」。所以施一次震术要捏两次，第一次锁宫，第二次蓄雷，中间还要先松开。

## 二、同一手势的多重含义

| 手势 | 设计里的含义 | 代码里的含义 | 靠什么区分 |
|---|---|---|---|
| 单手捏合 | 锁宫 | 锁宫；没有 Armed 时是**转盘**（`GestureStateMachine.ts:158`）；震术 READY 后是**蓄雷** | Armed 计时器（700ms）、术式阶段 |
| 双手捏合 | 无 | **抓起整个阵移动**（`GestureStateMachine.ts:147`） | 双手同时捏 |
| 双手张开 | 无 | **缩放阵局** | 双手距离变化 |
| 握拳 | 无 | 握 280ms **撤销术式**，握 800ms **收阵**（`GestureChoreographyController.ts:47,51`） | 握拳时长 |
| 张掌 | 起阵、施法 | 起阵、蓄势、坤／巽／坎施法的前置姿势 | 阵局和术式阶段 |

靠计时器分辨含义，真人操作时很容易被判到另一种意思上（锁宫变转盘的原因见 [PINCH_LOCK_DIAGNOSIS.md](PINCH_LOCK_DIAGNOSIS.md)）。

## 三、同一件事被判断多次

**判断层数。** 从摄像头到出招一共经过约 9 层：识别 → 平滑 → 状态机 → 优先级 → 编排 → 瞄准锁定 → 施法总闸 → 各术控制器 → 术式状态机。

**「算不算捏合」各层标准不一：**

| 数值 | 用途 | 位置 |
|---|---|---|
| 0.18 | 识别层认为在捏 | `GestureRecognizer.ts:87` |
| 0.18 进 / 0.25 出 | 平滑层稳定捏合 | `GestureSmoother.ts:45` |
| 0.30 / 0.24 / 0.20 | 锁宫：开始候选 / 计数 / 确认 | `TargetLockPinchDetector.ts` |
| 0.25 | 各术控制器认为已松开 | 坤／巽／坎／震控制器 |

**「先松手、再静止、再候选、再确认」这套流程**，四个术的控制器各写了一遍：坤、巽共用一个，震、坎各自一个。

## 四、残留代码

- `SectorFocusController.ts`：已没有任何地方调用，被 `TargetSelectionController` 取代。
- `GestureInputBuffer`：每帧写入，但只在调试面板显示，面板上标着 `cast caching OFF`（`main.ts:691`）。
- `main.ts` 约 800 行，坤／震／坎／巽各自的 QA 追踪代码和正式逻辑混在一起。

## 五、需要设计者拍板的问题

下面每个问题都会直接决定能删掉多少代码：

1. 锁定后要不要「蓄势」这一步？不要的话，第一节表里三行「无」都能删，施法动作可以在锁定后直接生效。
2. 单手捏合要不要兼任转盘？不要的话，捏合只剩锁宫一个含义，Armed 计时器和防抢占逻辑都可以去掉。
3. 双手抓阵、双手缩放还要不要？
4. 握拳要不要同时管「撤销」和「收阵」？只留一个的话，就不再靠握拳时长区分。
5. 震术的施法能不能换成不用捏合的手势？换掉的话，就不会和锁宫抢同一个动作。

定下来之后，建议按「删」的方向收拾，不要再加新的门。
